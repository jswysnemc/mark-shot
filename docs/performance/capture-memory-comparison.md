# Mark Shot 与 Babry 截图内存对照

本文件记录优化前的基线与原因分析。最终优化、性能复测及剩余差额见 [capture-memory-optimization.md](capture-memory-optimization.md)。

日期：2026-11-12。Mark Shot 为 `feat/native-barcode-scanning` 未提交工作区，Babry 为
`f10a1c669f2f2fd90ed1eaeab34d27a01474a749`，Babry 源码没有修改。

## 结论

差异存在，但不是固定三倍。相同隔离 Niri、同一空桌面和 release 构建下，1920×1080
起始选区阶段 Mark Shot RSS 为 62.36–62.67 MiB，Babry 为 13.61–13.67 MiB，约 4.6 倍。
4K 时分别约 160.5 MiB 和 37.3 MiB。两次复测趋势一致，空闲 CPU 均接近零。

主要原因是内存模型与实际依赖不同。共享 Rust、SCTK、wl_shm、tiny-skia 并不意味着
共享同样的像素所有权、缓冲数量、文字排版或功能代码。

## 条件

- AMD Ryzen 7 8845H，Linux，隔离 Xvfb + Niri，输出缩放 1.0
- 实际输出依次调整为 1270×720、1920×1080、3840×2160，检查 Niri 返回的逻辑尺寸
- 同一个空桌面；两个程序依次运行，单实例、不含后台托盘服务，不启动 OCR 模型或录制
- 起始选择和直接全屏编辑各测一次；每次启动后预热 2 秒
- 第一轮每组 15 秒，第二轮 10 秒，采样间隔 0.5 秒，期间不编译
- CPU 单个逻辑核心 100%；统计进程树 RSS/PSS，排除 Niri/Xvfb；全部 SwapPSS 为 0
- RSS 包含与合成器共享的像素页；PSS 分摊共享页。未计 GPU 显存和合成器的全部开销
- Mark Shot 使用中文、关闭指针放大区，Babry 使用默认界面；全屏编辑对照也保留显著差额

## 内存差额来自哪里

第一轮 1920×1080 起始选择，读取实际进程 `/proc/PID/smaps`：

| 映射类别 | Mark Shot RSS | Babry RSS | 解释 |
| --- | ---: | ---: | --- |
| 程序映射 | 20.26 | 1.75 | 已驻留的代码、只读数据与重定位页，不等于整个可执行文件大小 |
| Wayland 共享缓冲 | 15.82 | 7.93 | Mark Shot 两个整屏前后帧；Babry 一份原始截图及小型控件缓冲 |
| 匿名映射 | 16.80 | 0.18 | Mark Shot 约两份整屏 RGBA 像素，另有少量运行状态 |
| 堆 | 1.66 | 0.54 | 数据结构、缓存等，未做逐对象堆分析 |
| 字体文件 | 1.19 | 0.28 | 实际驻留字体页，远低于主要像素和代码差额 |

一份 1920×1080×4 像素为 7.91 MiB。Mark Shot 当前普通截图路径包含：

1. `ImageSource::store_snapshot` 保存原始 RGBA 像素，当前返回内存来源。
2. `app/layers.rs` 建立完整输出画布。
3. `overlay/frame_staging.rs` 维护最多两个原生 SHM 帧，活动帧保持只读，下一帧写入已释放槽位。
4. `frame_pixels.rs` 在提交后把已交付 CPU 前景清零，但合成路径没有归还这批匿名页。

4K 下 smaps 直接出现两块 32,404 KiB 匿名映射及一块 64,800 KiB SHM 映射，
对应上述四份屏幕尺寸缓冲。仅这部分约 126.6 MiB，解释了分辨率增长的大部分增量。

Babry `shm_image.rs` 的 `ShmImage` 让 screencopy 直接写入 memfd，`scene.rs` 把同一文件
用作冻结背景，导出按行读取。遮罩、边框、按钮采用子表面；标注瓦片按需触碰页面，释放后打洞。
因此普通 Wayland 截图的初始状态仅保留约一份整屏像素。
Babry 的 X11 和长截图另有完整软件合成路径，不能把这个结果直接推广到所有模式。

两者文字实现也不同：Babry `font.rs` 使用 mmap + ttf-parser 读取轮廓，Mark Shot 使用
cosmic-text 的排版与字形缓存。Mark Shot 同时链接 OCR 接口、扫码、图片格式、HTTP/TLS、
Portal/PipeWire 与更多编辑功能。本轮只把程序页按映射归类，不能把 18.5 MiB 程序页差额
精确分配给某个依赖。读取系统字体目录也不意味着整个字体文件都常驻。

本轮截图进程的映射中没有 `libmarkshot-media.so` 或 OCR 推理引擎；媒体库按需加载，
不是截图空闲内存差额的来源。

## 改进方向与边界

主要可减少的部分是重复的屏幕缓冲：让 Wayland 捕获和显示共用原始共享内存，
将透明遮罩、控件、标注采用小型表面或瓦片；同时保留软件合成作为不支持相关协议的后备路径。
这些改变涉及 RGBA/BGRA、分数缩放、wl_buffer.release、导出与字体绘制，不能只删除一个
缓冲或复用仍由合成器持有的帧。对于 CPU 前景，也可评估空闲时归还已清零的页，
但必须同时测量连续绘制时的缺页和 CPU，避免用内存数字换取交互退化。

本次按要求完成原因探查，没有把这种跨后端渲染重构混入已验收的界面改动。

## 复现与证据

```sh
uv run --no-project --python /usr/bin/python3 python scripts/performance/compare_capture_memory.py \
  --mark-shot target/release/mark-shot \
  --babry /home/snemc/workspace/babry/target/release/babry \
  --root /tmp/ms-memory-new --seconds 15
```

根目录必须是新的短路径，脚本只操作自己创建的私有桌面。每组保存截图、逐次采样、
完整 smaps 分类、命令和日志；两轮原始证据为 `/tmp/ms-memory-a/`、`/tmp/ms-memory-b/`。
