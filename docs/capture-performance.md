# 截图交互与长图内存分析

本轮针对整个程序的交互延迟检查共用绘制链路，鼠标移动只是产生连续输入的测试方式。
测试覆盖选区悬停、选区拖动、矩形、画笔、尺子与缩放；内存对照覆盖滚动增长、结果编辑及最终复制/保存。

## 三个实现的差异

分析源码为 `mark-shot-little` 的 `063edd3` 基础、Qt 项目的 `934d8f3`、
LumineCapture 的 `0b47dd5`。Qt 运行对照采用本仓库已有的
`target/qt-memory-reference-build-r1/mark-shot`，每份报告记录二进制指纹。
该参考构建不等于 Qt 仓库最新提交的重新构建；LumineCapture 本轮只比较源码。

| 环节 | 修复前当前实现 | Qt 实现 | LumineCapture |
| --- | --- | --- | --- |
| 冻结背景 | 超过 4 MiB 写入磁盘；合成时按 2 MiB 读取，随即清除映射页和文件缓存 | `QImage` 保留冻结帧，`QPainter` 按绘制事件区域使用它 | 截图、遮罩和图层保留在内存 |
| 原生提交 | 前景转 BGRA、透明共享页打洞、消费前景页、再写入不透明背景；备用缓冲释放后立即回收 | Qt 管理窗口 backing store 与提交 | 直接进行通道转换及范围复制 |
| 选框 | 固定 1024 像素分块包含大量完全透明的内部区域 | 绘制选框路径 | 常规路径绘制 |
| 尺子 | 外层 512 像素分块重复调用自身 1024 像素分块；不可见数字也排版 | 画布中的尺子绘制 | 不具备当前版本全部尺子功能，不能直接等价比较 |
| 长图存储 | 固定像素块增长，预览借用视图，没有完整预览副本 | Rust 拼接核心之外，`Stitcher::fullImage()` 维护 Qt 完整图像缓存 | 连续缓冲约 1.5 倍扩容；预览通过 `full_image()` 获取完整图像 |
| 捕获交接 | 完整输出帧在裁切和拼接期间持续存活；重复帧先裁切再判断 | 独立滚动会话及 QImage 数据共享 | 同步捕获、裁切及拼接，预览还存在定期重绘 |

源码定位：Qt 的 `qt/src/shot_window_canvas.cpp`、`qt/src/scroll/stitcher.cpp`；
LumineCapture 的 `src/app/scroll.rs`、`src/backend/wayland/utils/shm.rs`、
`crates/shot-stitch/src/long_image.rs` 和 `src/scroll/session.rs`。
三者差异不能简单归因于编程语言或声称 Qt 使用 GPU 而当前实现没有使用 GPU。

## 确认的问题与修改

1. **冻结背景的磁盘重读阻塞绘制。** 恢复唯一冻结帧的共享内存所有权，既有分析任务继续共享，
   进入滚动会话后释放。长图编辑原件仍使用文件缓存，避免把完整长图重新常驻为多个副本。
2. **透明页回收与随后写入背景相互抵消。** 新增 `backend/composited_pixels.rs`，直接将前景、
   背景与通道转换合为一次写入。消费路径仅清空已交付范围，不再扫描和回收整幅 CPU 前景。
   整帧透明背景恢复也保留已分配页，避免下一次提交再次产生大量缺页。
   不透明模式保留已释放的备用缓冲；仍然只允许修改服务端已释放的槽位，最多两个缓冲。
3. **空心图形处理大量空白像素。** 选框采用固定 128 像素边缘块，跳过保证透明的内部块。
   `selection_border_damage.rs` 在复制背景前计算四边损坏交集，不为只画边框复制整个选区。
   原有完整路径与新路径在分数比例、负坐标和圆角下逐字节比较。
4. **尺子重复分块及排版。** `renderer/pending_ruler.rs` 直接使用尺子自身的固定栅格，
   先按正文边界限制背景复制；刻度在排版前先检查包含描边、旋转和采样余量的可见范围。
   `ruler_hover_damage.rs` 将十字线和标签合并为互不重叠的窄区域，避免整窗透明层，
   交点仍只合成一次。保留原有像素和标注尺寸。
5. **滚动帧生命周期过长。** 在原始捕获帧上读取相同的 18×24 亮度签名，重复帧不再创建裁切图。
   变化帧裁切完成后立即释放完整输出帧，再进入拼接。签名、行距、边界和原图结果有回归覆盖。

修复前的短时间系统调用采样（包括测试进程树）记录约 19.5 万次 `madvise` 和 701 次 `fadvise64`，
保存在 `target/performance-syscalls-before.txt`。仅恢复背景内存复用时，三个基础场景从
约 7–11 帧/秒上升到约 19–30 帧/秒；其余修改继续处理共同提交成本与工具独有成本。

## 测量方法与边界

`scripts/wayland-pointer-performance.py` 在私有 3840×2160、比例 1 的 Sway 输出中，
以每秒 120 次输入驱动相同路径，统计实际完整窗口缓冲附着次数与帧间隔。
它识别 Rust、Qt 两种协议日志格式，排除光标表面，保存可见终态并检查活动缓冲复用。
默认每场景测量三秒，至少 45 次完整帧提交/秒才通过；这不是显示器实际扫描输出的测量。
只读检查确认宿主桌面为 niri，输出为 2560×1600、比例 1、240 Hz。
本轮性能数字来自隔离 Sway，不能当作该 240 Hz 桌面上的帧率实测。应用继续由合成器帧回调调度，
没有为了测试新增 60 帧上限；150 ms 只作为帧回调异常时的兜底期限。

长图测试采用相同确定性纹理、3200×1800 选区、256 次各 48 像素滚动，得到
3200×14088 原图。25 毫秒采样同时计入应用子进程、未映射原件缓存及原生共享文件额外驻留，
按文件身份去重；RSS 与 PSS 分开保存。参考页面和合成器不计入应用。

修复前该长图场景未复现“当前版本内存为 Qt 两倍”：当前构建观测峰值约 369 MiB，
Qt 参考构建约 906 MiB。因此不能把本场景数据当作用户现场“翻倍”问题已经复现或解决的证据。
后续补测确认这套流程遗漏了最终复制、通知和脱离父进程的剪贴板服务，完整交付结果见后文。

冻结帧和备用缓冲恢复复用会增加普通截图的常驻内存，这是去除每帧磁盘读取和页面反复分配的
明确取舍；不能用较低的旧 RSS 数字描述新构建。滚动开始会释放这些普通截图资源，
滚动期间的变化主要来自裁切和拼接生命周期。

也会触发该保守检查，因此没有据此判定 Qt 存在缓冲写入错误。Qt 帧率对照需要另行统一表面
和内容更新口径；本轮可靠的帧率增益来自同一 Rust 程序修复前后对照。

## 第一轮长图结果编辑内存

同一 3200×14088 长图，单位 MiB，采用 RSS 加未映射但仍驻留的原件/原生共享文件页。
下面是单次流程采样，不能将约 1–2 MiB 的差值解释为稳定性能收益。

| 指标 | 修复前 Rust | 修复后 Rust | 本次 Qt 参考 |
| --- | ---: | ---: | ---: |
| 全流程峰值 | 368.84 | 369.51 | 890.32 |
| 滚动稳定阶段中位数 | 235.57 | 233.98 | 736.37 |
| 长图结果编辑中位数 | 63.87 | 156.62 | 281.22 |

结论：当前场景下滚动阶段内存基本持平，没有证据支持“总峰值降低一半”。
提前释放捕获帧和重复帧免裁切消除了不必要的同时存活与分配，但没有显著改变本场景全流程峰值。
结果编辑需要复用普通交互缓冲，常驻内存增加约 93 MiB；增加的是屏幕大小缓冲，没有新增完整长图副本。
原件文件为 180326400 字节，与 3200×14088×4 一致；滚动控制共享映射保持 2248704 字节，
低于 4 MiB 门槛，进入滚动后不再保留整屏控制缓冲。

原始记录：`target/performance-before-scroll5/result.json`、`target/performance-after-scroll/result.json`。
原有内存脚本要求“所有指标均低于 Qt 一半”，本次退出码为 1：结果编辑 RSS 比例为 55.7%，
未通过这个既有门槛；捕获、原图交接、共享映射预算、取消恢复及退出清理均通过。
应保留这一失败记录，不以滚动阶段数据替代结果编辑数据。

另对系统安装的 `mark-shot-bin 0.1.62-1`（`/usr/bin/mark-shot`）执行同一流程。
其 SHA-256 为 `2741b92725ced23761944de5c6d60a761bc3625778f7e8b8a3a3c9dfe619316a`，
Qt 峰值为 902.19 MiB、滚动稳定中位数为 747.34 MiB。该轮 Rust 原始样本峰值为 366.52 MiB、
滚动稳定中位数为 234.25 MiB、结果编辑中位数为 156.87 MiB，与前一轮结论一致。
记录位于 `target/performance-system-qt/`。

系统版本补测没有整体通过：末尾共享映射预算断言将 `scroll-first` 采样时恰好存在的
32400 KiB 捕获映射（RSS 为零）与 2196 KiB 控制映射相加，误报控制栏持有整屏缓冲。
该断言按同名 memfd 汇总，不能区分捕获与控制资源；后续滚动稳定映射仅 4388 KiB。
保留原始失败和样本，不将这一轮报告为完整验收通过。两个版本差异均不足以解释用户反馈的翻倍，
但这轮只到结果编辑器，没有覆盖最终复制；后续完整交付复现了接近用户截图的峰值。

## 完整复制流程复现与修复

补充通知服务并追踪脱离父进程的剪贴板服务后，同一 3200×14088 长图复现 **600.38 MiB** 峰值。
此前只统计主进程及其子进程，会漏掉双重 fork 后长期存活的图片剪贴板服务。
用户提供的约 576 MB 截图与这个量级相符，但不能据此断言发生在完全相同阶段。

三个额外问题均已修复：

1. 通知缩略图原来通过 `image::load_from_memory` 解码完整长图。现在复用逐行 PNG 解码器，
   仅保留有限行缓冲与 256 像素缩略图，解码预算为 4 MiB。
2. 图片剪贴板原来先 `read_to_end(Vec)`，依赖内部再从 `Vec` 复制到 `Arc`；交付后辅助进程仍持有
   约 205 MiB。现在按 64 KiB 接收至匿名文件，通过 ext-data-control 或 wlr-data-control 提供数据，
   每次粘贴独立偏移并流式发送。文件随服务结束自动删除，同时保留普通剪贴板、primary 和 KDE MIME。
3. PNG Fast 编码对高熵长图输出约 196.7 MB，超过 RGBA 容量预留。现在采用 deflate level 1，
   同图约 119.5 MB；复制逐行编码时释放已经写完的纵向块。保存保留借用路径以支持取消后恢复。

所有采样均包含 RSS、原生共享页及未映射但仍驻留的原件/剪贴板文件页，间隔 15 ms。
脚本按私有配置目录发现独立辅助进程，默认历史记录等选项开启，通知通过私有 DBus 接收。
指标字段 `original_file_resident_kib` 也包含 `clipboard` 类文件，明细可以区分。

| 指标（MiB） | 完整复制修复前 | 完整复制修复后 |
| --- | ---: | ---: |
| 整个流程峰值 | 600.38 | 318.44 |
| 复制阶段峰值 | 600.38 | 235.73 |
| 交付后的辅助进程及文件页 | 204.86 | 18.06 |
| 粘贴阶段峰值 | 未单独验证 | 22.51 |
| 取消剪贴板所有权后残留 | 未单独验证 | 0 |

修复后整个流程峰值出现在滚动增长阶段，不能把滚动阶段样本波动解释为编码优化收益。
保存分支整个流程峰值为 382.16 MiB，已完成保存并退出。这里没有同动作 Qt 复制数据，
不把前文 Qt 结果编辑器数字用于复制阶段排名。

记录：`target/scroll-notify-tree-before/result.json`、`target/scroll-memory-final/result.json`、
`target/scroll-save-final2/result.json`。内存修复构建为 `target/performance-memory-fixed2`，
SHA-256 为 `048e0b909fb272cddb2526c5609ac6d4d1bf3d20d7cc06f1d99d7f2b23761640`。
前一构建为 `target/performance-scroll-before`，指纹见绘制验证记录。

四种协议/选择组合在 `target/clipboard-protocol-fixed2/result.json` 中通过：ext 普通/primary 峰值
均为 22.05 MiB，wlr 普通/primary 为 22.26/22.19 MiB。每种组合连续粘贴两次，PNG 字节一致，
尺寸正确，KDE MIME 返回空数据，接管后服务退出。完整复制流程通知缩略图为 58×256。

第一次文件服务验证在 btrfs 上仍出现约 130 MiB 文件缓存，原因是预读与 64 KiB 回收不足。
最终版本关闭预读、按 4 MiB 批量回收，发送结束后再次回收全文件；保留失败记录
`target/clipboard-protocol-fixed`。第一次保存测试因私有 Sway 对话框未聚焦而超时，修复测试输入
聚焦后通过，失败记录保留在 `target/scroll-save-final`。

## 工具交互与图片编辑对齐

新增交互修复与原有渲染优化共用同一条输入、撤销和原图导出链路：

- 选区八个把手常驻。每个把手只生成固定物理原点的小块，完整绘制后裁切损坏范围，
  避免分数比例的局部重绘反复叠加抗锯齿边缘。
- 选择工具单击文字正文即进入编辑并显示插入光标，后续单击定位插入点；控制点仍可调整文字框。
  普通文字随输入扩展和收缩，已发生软换行的框保留换行宽度，旋转文字先反变换点击坐标。
- 工具栏垃圾桶清空全部标注、活动文字及未提交图形，保留撤销恢复；独立对象的删除按钮继续删除选中对象。
- 完成绘制后的画布滚轮优先选择最后一个同类标注，再调整实际属性。文字包括已提交、正在新建和重编辑三种状态，
  隐藏属性面板不影响字号调整，文字输入时不误缩放图片。
- 数值步进使用更小、更细的圆端矢量箭头；取色加入普通工具栏，HEX 和 RGB 复制位于现有选项面板。
  窄窗口先适度压缩按钮尺寸，再换行，避免新增一个工具便扩大整行遮挡。
- 缩放及图片编辑采用 Qt 的固定十二逻辑像素棋盘格，两色为 `(51,55,62)`、`(60,64,72)`。
  棋盘格锚定窗口，不跟随图像缩放，翻译局部恢复也保持相同相位，导出不包含底纹或把手。
- Wayland 图片编辑改用普通可调整窗口，默认选择标注工具，显式工具配置仍优先。
  窗口尺寸协商只重建显示缓冲和视图，不改写原图、标注、选区及撤销历史。

Qt 的实际入口是 `qt/src/annotation_launch.cpp::openImageForAnnotation`，原先当前实现直接创建全屏覆盖层，
并非单纯背景颜色不同。私有桌面验证记录在 `target/image-window-native` 与 `target/image-window-qt2`：
两版均经过多次窗口调整并复制完整透明原图，导出逐像素一致。Qt 第一轮尺寸协商未在固定等待时间内达到请求值，
失败记录保留在 `target/image-window-qt`；Qt 对照不以固定尺寸断言作验收，后两次实际尺寸与请求一致。

缩放采用可见区域轴向双线性采样，预计算列坐标，最多四个线程，四通道使用独立整数槽同时插值。
像素参考覆盖透明、半透明、不透明、分数覆盖和不同倍率，插值与通用光栅器最多相差两个色阶，
这里只影响显示采样，导出继续读取原始像素。完整不透明帧直接转换通道，跳过旧背景混合。

后续分段计时确认，4K 连续缩放中背景采样与底纹约 6.8 ms，串行遮罩额外约 9.4 ms。
遮罩整数内部改为共用同一个四线程池，分数边缘继续使用原路径抗锯齿；逐像素对照保持完全一致。
线程池按独占行带写入，不建立额外完整图像。测量日志在 `target/zoom-diagnostic7/zoom/client.log`。

长图编辑还存在独立问题：每帧释放唯一原件文件映射的干净页，导致下帧重新读取长图。

## 中文界面仍占用 600 MiB 的复查

用户反馈重新编译后滚动截图仍达到 600 MB。此前的 318.44 MiB 来自较早构建，且压力脚本
强制英文、启动后立即选择区域，因此没有覆盖中文界面在后台系统字库合并后的执行路径。
这一结果不能证明用户反馈已经解决。

使用反馈时的发布二进制 `ed054f271bcbe287095f30bebc292f0f4d9f6e56c89e75311bc751901b1c405a`
重新测量，相同 3200×14088 长图的英文流程峰值为 284.35 MiB；中文界面等待启动 3 秒后，
滚动首帧达到 628.25 MiB、增长峰值达到 896.79 MiB。记录分别位于
`target/scroll-current-check2/result.json` 与 `target/scroll-font-before/result.json`。

根因在 `fonts::ui_fallback::ensure_text`：它将字体数据库中所有条目视为已经加载的字体，
逐一调用 `FontSystem::get_font` 后才检查中文字符是否存在。后台线程合并的是系统字体目录，
因此一次中文状态绘制就解析并缓存了大量不相关字体。首帧映射中，35 个超过 1 MiB 的字体
映射合计驻留 211.73 MiB，另外还有排版引擎生成的堆缓存。系统字库是否赶在选择区域前合并，
导致同一构建有时正常、有时增加数百 MiB；这也是此前短流程测试漏检的原因。

修复将缺字检查改为按实际字符通过平台字体匹配确定家族，仅解析所需字重的字体。
OCR 正文和选区尺寸面板复用同一逻辑，分别保留 Noto Sans 和半粗体需求。
没有改动长图像素、拼接算法、原图分辨率或截图缓冲策略。

回归测试将 32 个带访问计数的无关字体加入系统目录，要求中文准备和重复绘制始终零访问；
同时验证常规和半粗体中文实际排版没有缺失字形。压力脚本默认使用中文并等待 3 秒，支持
`--entry shortcut` 从普通截图经快捷键进入滚动，且分别对增长阶段、复制阶段和剪贴板服务
设置内存阈值。

## 窗口尺寸调整的未绘制缓冲

图片编辑窗口的 Wayland 配置回调曾在收到新尺寸后立即附着并提交新 SHM 槽位，应用尚未
绘制该槽位。槽位复用时可能把旧图像按新行距显示为花纹。现改为在尺寸变化时只准备槽位，
待应用完成新尺寸的整帧绘制，再统一提交缓冲、视口及损坏范围；首次映射的占位缓冲明确清零。

图片视图使用原件变换采样时，调整窗口不再额外生成整屏冻结预览，减少重复缩放和原件页回收。
`scripts/wayland-image-editor.py` 增加协议断言：首个实际绘制帧之后，每次缓冲附着都必须属于
一次完整绘制提交。对旧日志 `target/image-snapshot-final/app/client.log` 执行该检查会失败，
记录在 `target/resize-before-check2.log`；原图逐像素导出检查继续保留。
