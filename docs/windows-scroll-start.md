# Windows 长截屏启动修复

2026-11-12，基线提交为 `8e9cc3b7429db2ea43d320bb3678481faafa0dfd`。

## 原因与复现

Windows 原生覆盖层没有实现 `ScreenOverlay::begin_scroll` 和
`stage_scroll_panel`。框选完成后，共享长截图流程调用默认接口并退出：

```text
scroll capture requires an overlay with on-demand keyboard focus
```

失败发生在建立持续捕获会话之前，与 GIF 校验工具、录屏编码器或拼接匹配无关。
从 Windows 工作流 `43209217772` 下载的实际产物也能复现，EXE 的 SHA-256 为
`cbd6d4d3c972b0e9cfdf7c9dcb1f669942b9f9e983b0d889ea36758f48063946`。

独立 Wine/Xvfb 下启动 `--scroll`，在 `(100,120)-(400,420)` 框选，旧产物退出码为 1。
同一启动脚本对修复候选返回成功。原生窗口回归在修复前因同一接口错误失败，修复后通过。

## 修复行为

- Windows 在原显示器上创建局部控制面板，保留显示器与表面索引的绑定
- 进入长截图时隐藏全部冻结覆盖层并释放原生完整屏幕位图，持续捕获仍使用已有 GDI 会话
- 面板首帧不抢占焦点，恢复仍存在的原窗口；用户点击控件后才请求键盘焦点
- 原生客户区鼠标坐标转换为原显示器坐标，按钮、预览和方向拖动使用共享输入流程
- 控制面板与选区重叠时隐藏面板，丢弃在途帧并请求干净帧，静止暂停后恢复操作界面
- 保存对话框取消后恢复原面板，重新创建普通截图表面时清除长截图状态

窗口与避让实现在 `src/backend/windows/overlay/scroll.rs`，接口及生命周期在
`presentation.rs`，输入转换在 `events.rs`。原生窗口只补充聚焦与位图回收方法。

## 验证

证据保存在 `target/windows-scroll-diagnosis/`。测试使用独立显示和私有 Wine 前缀，
没有连接用户桌面。测试页面使用确定性文档纹理，期望像素由独立验证脚本生成；
复制结果通过独立 Windows API 程序读取系统 PNG 剪贴板。

| 场景 | 结果 |
| --- | --- |
| 框选启动 | 同一复现脚本从失败变为成功 |
| 纵向滚动三次，每次 48 像素 | 导出 300×444，全部 RGBA 与独立原图一致 |
| 横向滚动三次，每次 48 像素 | 导出 444×300，全部 RGBA 与独立原图一致 |
| 1260×780 大选区，面板无法避让 | 干净帧捕获、静止恢复控件后复制，全部 RGBA 一致 |
| Windows 长截图窗口回归 | 5 项通过，涵盖启动、无效目标、真实鼠标消息、污染帧隔离及暂停恢复 |
| Windows 已有输入及原生资源回归 | 11 项通过 |
| Linux 共享长截图应用测试 | 8 项通过 |
| Windows MSVC 全工作区、全目标严格 Clippy | 通过 |
| Rust 格式与补丁空白检查 | 通过 |

长截图测试分组已加入 `scripts/windows-test.ps1` 和私有 Windows 单元测试脚本。
本次修复候选 EXE 的 SHA-256 为
`62d6ac96e8e3f052b7136b9df51dd0246bee3a50e4de834ba157ff0cf2b062f9`。

这些结果证明已执行的 Win32/Wine 路径与图像交付行为。真实 Windows 多显示器、
不同 DPI 和桌面合成器行为尚未实机验收；这些记录来自提交前本地验证，不包含远端工作流结果。
