# 0.1.62 内存回归排查与优化

日期：2026-11-01。目标：分析并解决相较上一版明显增长的内存占用，进行多轮调研、优化和完整操作链路复验。**已完成本机可复现回归的定位、修复及多轮验证；结论限于下述场景与平台，不代表所有使用场景均曾翻倍或已经得到全平台验证。** 官方资料见[内存优化一手资料](memory-regression-references.zh-CN.md)。

## 对照边界

- 上一发行版取 `v0.1.61`；当前源码基线为 `1e3877d`（0.1.62），包含前一轮尚未提交的录制及剪贴板修改。两份源码已独立保存，均用相同 Qt 6.12.0、GCC 和 Release 配置构建。
- 首轮使用隔离配置与 Qt offscreen，图片全部合成，不读取用户截图、不连接真实桌面。offscreen 能用于进程/模型/图片生命周期对照，不能代表 Wayland/GPU 开销已验证。
- 本机 `/usr/bin/mark-shot` 是 0.1.62 安装版；`~/.local/bin/mark-shot` 指向另一个工作目录的程序，自报 0.1.61，且该目录 Git HEAD 与二进制版本不同。不能把这个二进制当作可复现源码基线。用户实际观察的入口及场景仍待确认。
- 记录 RSS、匿名驻留、文件驻留、PSS、私有页和子进程。PSS 与 RSS 分开，不能将共享库重复计费或把工作集裁剪当作释放活对象。

## 第一轮：复现与最小化

### 没有 OCR 插件的 GUI 对照

每个场景用 1920×1080 合成图，重复三个操作周期；下表为该进程峰值 RSS，不是多轮统计中位数。

| 场景 | 0.1.61 | 当前源码 |
| --- | ---: | ---: |
| 截图选择 | 105.27MiB | 105.89MiB |
| 标注 | 91.31MiB | 91.71MiB |
| 图片编辑 | 101.36MiB | 101.73MiB |
| 贴图 | 62.73MiB | 63.38MiB |
| 贴图后编辑 | 99.04MiB | 99.82MiB |
| 设置窗口 | 81.68MiB | 81.80MiB |

此处未复现翻倍。真实程序入口的空托盘和空历史窗口也接近：约 50MiB 和 65MiB。尚未用这个结果排除大量历史条目、复杂画布或真实合成器下的增长。

### 相同 OCR 插件和模型下的贴图

在两版隔离用户目录安装同一份 `rapid-onnx` 插件，使用相同 PP-OCRv5 mobile 检测、识别模型及字典，不加载其他个人配置。只打开一张合成图片，不点击、不拖选、不录制。

首轮每 50ms 采样的三轮最大 RSS：旧版约 58MiB，当前中位数约 166MiB，比例约 **2.85 倍**。这只是采样最大值，不是完整峰值。后续复核同一批原始 JSON 中的内核 `VmHWM`，当前三轮实际高水位为 **207.26、206.97、210.85MiB**，中位数约为旧版的 **3.55 倍**。当前识别结束后的驻留约 91MiB，约为旧版 **1.57 倍**。日志确认当前版在贴图显示后自动加载了 `rapid-onnx`，旧版在这个未交互的操作中没有执行识别。

因此目前证据证明的是：新增后台预识别改变了相同打开动作所执行的工作量，出现显著推理峰值和额外驻留；并非所有空闲界面都同比翻倍。也不能把“旧版没有做 OCR”与“新版已完成 OCR”当作相同工作量下的编码效率对照。

已运行的自动回归命令：

```sh
python3 build/memory-regression/check_pin_regression.py
```

旧代码三个回合均返回回归，历史输出包含 `REGRESSION ... peak ratio 2.85 ... settled ratio 1.57`；其中 peak 当时实际使用采样最大值。探针现在分列 `peak_root_rss` 与 `peak_root_hwm`，门禁改为使用后者并以新文件前缀保留结果，不覆盖原始证据。末段取第二秒之后的样本，不把识别过程最高点当成常驻值。现有阈值用于追踪本次回归，不代表产品已经确定了统一内存预算，更不代表执行额外 OCR 工作后推理峰值应与未推理旧版相同。

### 已排除与待检验判断

1. 现有代码已关闭 ONNX CPU arena 和 memory pattern，并在识别结束释放会话，还主动归还空闲堆页。“关闭内存池”或“结束后释放模型”不是新的修复。
2. 检测和识别模型在开始检测前同时加载。若它们造成峰值叠加，分阶段加载应降低峰值；以完整 token、坐标及置信度对照排除文字结果退化。
3. 每个 Session 使用逻辑处理器数量一半的 intra-op 线程；如果线程工作区是主因，降低线程数应明显省内存。必须同时测量识别延迟，不能只看 RSS。
4. 多任务在插件内部互斥前已经分别解码完整图片，取消/超时只断开结果通知。如果这是并发增长来源，应能在真实任务类中复现同时持有多张图片以及放弃任务继续调用模型。
5. 识别后还存在新增文件驻留和匿名页；后续须分别检查运行时常驻页、线程缓存和活对象，不能仅凭 RSS 推断泄漏。

## 第二轮：模型工作区实验

在独立目录编译生产插件的实验副本；使用三种合成图：密集小文字、较大文字和空白图。每个配置三次，图像、模型和字典相同。这里是插件接口级测试，不包含完整 GUI 或排队任务。

| 密集文字配置 | 峰值 RSS 中位数 | 耗时中位数 | 识别 token 数 |
| --- | ---: | ---: | ---: |
| 原始双会话同时加载，8 线程 | 167.20MiB | 657ms | 262 |
| 分阶段加载，8 线程 | 146.68MiB | 696ms | 262 |
| 分阶段加载，4 线程 | 146.09MiB | 710ms | 262 |
| 分阶段加载，2 线程 | 145.24MiB | 918ms | 262 |
| 分阶段加载，1 线程 | 145.77MiB | 1394ms | 262 |

五种配置在三类图片中的 token 文字与坐标一致，置信度差异通过 `1e-5` 上限。大文字原始/分阶段配置为 168.24/146.50MiB、242/263ms；空白图为 169.30/145.82MiB、170/122ms，后者无需加载识别模型。

决定：采用检测后释放检测会话、再加载识别会话的生命周期；不默认降为单线程，因为内存收益很小但延迟增加明显。原有默认线程数暂时保留。

额外进行了 `ALL -> EXTENDED/BASIC` 图优化等级对照。EXTENDED 约为 140～142MiB，三个样本的 token/坐标一致，置信度存在约 `3.7e-6` 差异。这组样本不足以覆盖不同模型与文字，不直接修改生产默认等级。

错误语义边界：缺失模型文件仍在启动前拒绝；没有检测框时不再加载识别模型，因此不会提前发现未被使用的识别模型损坏。需要识别文字时，识别模型/字典加载失败仍返回错误。不能声称所有异常路径与旧实现完全等价。

## 第三轮：任务排队与取消

新增回归使用真实 `OcrPluginTask`，仅把同步 OCR 插件替换为可控阻塞实现，模拟 Rapid 插件内部互斥。旧代码已经得到四个确定失败：

- 同时进入插件并持有已解码图片的任务数为 4，而不是 1。
- 排队任务显式取消后仍然调用模型。
- 排队任务对应对象销毁后仍然调用模型。
- 排队任务超时后仍然调用模型。

单独 4K 图片压力用例三轮高水位：旧版为 151632、151732、151688KiB，修复后为 54136、54192、54256KiB，约减少 64%。这是任务缓冲压力测试，不包含 ONNX 推理或完整贴图窗口，不能作为整个应用的降幅。

实现范围：

```text
qt/src/providers/ocr/
  ocr_task_executor.{h,cpp}    独立单工作线程，在解码前准入
  ocr_plugin_task.{h,cpp}      共享取消标志、单次启动、生命周期结束后归还空闲页
qt/tests/
  ocr_plugin_task_lifecycle_test.cpp  阻塞任务、取消、超时、析构和结果通知回归
```

排队任务只保留路径与取消状态，仍然保留每张有效贴图的识别请求，不用丢弃其他窗口结果换取低内存。正在同步推理的插件不能强行中断；取消后丢弃结果，未开始的任务在解码前退出。代价是独立插件 OCR 任务串行，必须继续测量多窗口完成延迟和前台请求体验。

任务回归已经通过；随后补充启动前取消、重复启动、执行中超时/销毁、缺失图片和插件失败测试，均通过。`ocr-provider-factory` 同时通过。`ocr-plugin-task-lifecycle` 和下一轮新增的图像输入测试通过 ASan/UBSan；关闭 LeakSanitizer，系统 Qt/ONNX 库未插桩，不能据此宣称全进程无泄漏。

## 第四轮：输入像素共享与长期驻留归因

### 保持识别结果的输入共享

直接取消 RGB32 到 ARGB32 转换会改变 Qt 的平滑缩放分支，密集文字样本 token 数从 262 变为 257，已拒绝采用。替代方案保留 ARGB32 解释，但为不透明 RGB32 创建持有原 QImage 引用的只读视图，避免再次分配完整源图；其他格式和异常 alpha 沿用原转换。

新增 `qt/plugins/ocr-rapid/rapid_image_input.{h,cpp}` 与 `qt/tests/rapid_image_input_test.cpp`。测试先以原转换实现得到三个共享断言失败，再验证修改后通过；覆盖源图析构、源图写时复制、结果写入、外部缓冲清理、行填充、透明/预乘格式、空图、DPR/色彩空间及两种缩放尺寸的逐像素一致性。

实验副本三种图片各三次，完整 token JSON（含置信度）与原始结果精确一致；密集文字的插件接口高水位中位数由分阶段实现的 146.68MiB 降至约 138.66MiB。正式拥有源图寿命的实现也完成九次完整 token 对照，密集文字中位数为 138.39MiB、639ms。此处是插件入口，不能与完整应用高水位直接相减。输入检查额外扫描透明位，但不分配第二张全尺寸图；没有改变模型分辨率、线程数或图优化等级。

同一完整应用入口、图像与模型交错测量三轮，稳定值取第 3～7 秒样本的中位数，再按三轮取中位数：

| 完整入口状态 | 内核高水位 | 稳定 RSS | 稳定匿名驻留 | 稳定 PSS |
| --- | ---: | ---: | ---: | ---: |
| 0.1.61，不执行自动 OCR | 58.63MiB | 58.63MiB | 15.16MiB | 43.46MiB |
| 当前修改前基线，后台 OCR | 207.26MiB | 91.38MiB | 29.52MiB | 75.79MiB |
| 分阶段加载、任务准入及输入共享 | 177.09MiB | 91.03MiB | 29.01MiB | 75.42MiB |

已实施部分将高水位降低约 14.6%，但稳定期 RSS 几乎不变。结果保存在 `results/cli-owning-input-summary.json`；探针、程序和插件使用明确绝对路径，不依赖同名程序的 PATH 优先级。

### 自然空闲 45 秒与 QtGui 线程池对照

| 独立完整应用条件 | 45 秒后 RSS | 匿名驻留 | 线程变化 | 内核高水位 |
| --- | ---: | ---: | --- | ---: |
| 0.1.61，打开贴图不执行 OCR | 58.54MiB | 15.16MiB | 最终 2 | 58.54MiB |
| 分阶段模型加载，QtGui 池默认 | 90.95MiB | 29.06MiB | 10，约 30 秒后降至 2 | 185.73MiB |
| 分阶段加载，独立进程禁用 QtGui 池 | 90.46MiB | 28.74MiB | 最终 2 | 185.34MiB |

这组完整应用尚未包含随后加入的输入共享。QtGui 线程自然退出后没有明显 RSS 下降，禁用它也只减少约 0.49MiB，不能解释主要驻留差异。因此不把私有环境变量作为生产全局优化。

稳定期 smaps 显示 ONNX 运行库映射约 15.39MiB，大部分为文件来源的 `Private_Clean`；另有约 13.90MiB 匿名差额。前者并不是存活堆或泄漏，后者还需继续区分运行库全局状态、分配器保留及窗口对象。Session 和 `Ort::Env` 已释放，不代表平台单例、算子/schema 注册及代码映射也随之释放。

### 卸载实验与风险边界

独立诊断用新 QPluginLoader，在关联路径之前取消默认 PreventUnloadHint，十轮顺序识别后卸载并整理空闲页。若在主线程推理，十轮 `unload=true` 但 ONNX 仍映射，卸载后 RSS 约 52.93～53.58MiB；若在短生命周期线程推理，线程退出后由主线程卸载，十轮 ONNX 均不再映射，RSS 约 26.81～28.08MiB。两条链路每轮均有 262 个 token，但此实验没有逐 token 比较，不视为识别等价性验收。

此结果支持推理调用线程的存续影响运行库回收，不足以定位某个具体 TLS 对象。也不能将该诊断直接接到现有注册器：注册器及排队任务借用插件裸指针，元信息或结果的 QString 可能仍引用插件静态数据；卸载成功不会等待活动调用。本阶段没有改变正式代码的卸载策略，也没有引入 OCR 子进程。第六轮继续保持插件本体驻留，仅管理独立运行库寿命。

## 第五轮：独立 ONNX 运行库寿命原型

在忽略目录 `ocr-experiments/dynamic-ort/` 复制当前插件，试验 `ORT_API_MANUAL_INIT`：插件本体只链接 Qt，运行时通过 QLibrary 查找 ONNX API 表；保持插件互斥，短生命周期线程完成模型加载、识别及模型释放，线程退出后调用 `Ort::InitApi(nullptr)` 并卸载运行库。插件本体不卸载，没有创建子进程。**后续检查证实 ONNX 1.29 的 `InitApi(nullptr)` 不会清除缓存表，这个原型存在悬空 API 指针，不是可发布实现。** 下述历史数据仅证明资源分离方向，不证明原型安全；正式实现改用局部 C API。

三种图像各三轮完整 token JSON 与当前修复版精确一致。完整应用使用原型插件进行三轮单贴图，得到内核高水位中位数 **177.38MiB**、稳定 RSS **64.77MiB**、匿名驻留 **17.95MiB**、PSS **49.19MiB**。与生产候选的 91.03MiB 相比，稳定 RSS 少约 26.26MiB；与旧版未执行 OCR 的 58.63MiB 相比仍多约 6.14MiB。高水位没有明显进一步下降，收益来自识别完成后的资源回收，不是少执行 OCR，也不是把内存转移到子进程。

另用默认保持插件加载的独立进程连续调用十次，完整 token JSON 的 SHA-256 每次一致，ONNX 映射每次在返回后消失；主动 trim 后 RSS 从首轮 29.77MiB 至第十轮 30.89MiB。该探针保留同一个插件实例，不等同于十次启动进程；结果在 `results/ocr-repeat-dynamic.json`。这仍不是长时录制、多窗口或无泄漏证明，也不能用主动 trim 后的接口 RSS 替代完整应用稳定值。

数据位于 `results/ocr-dynamic-ort-summary.json` 与 `results/cli-dynamic-ort-summary.json`。当前原型仅按本机库名查找运行时，尚未具备正式错误恢复、API 指针 RAII、线程创建失败处理、私有运行库定位及跨平台兼容；不能直接复制到正式插件发布。生产化必须保留现有运行库冲突回退，并验证反复调用、取消关闭、多贴图、模型失败、缺失/旧版运行时和 Windows 打包。

## 第六轮：局部 C API 与运行库回收

正式实现不使用 `onnxruntime_cxx_api.h`、`Ort::InitApi` 或静态 API 缓存。插件继续驻留，运行库在任务中加载；检测、识别模型与全部原生句柄均在短生命周期线程内释放，线程退出后再解除运行库映射。返回的文字、坐标、置信度均为 Qt 自有值，不携带原生指针。

```text
qt/plugins/ocr-rapid/
  rapid_runtime_paths.{h,cpp}  显式覆盖、插件私有目录、应用目录及系统运行库定位
  rapid_onnx_runtime.{h,cpp}   加载引用、版本校验、线程退出与运行库释放
  rapid_onnx_handle.h         按局部 C API 释放原生句柄
  rapid_onnx_session.{h,cpp}  输入字节数检查、会话和输出数据所有权
  rapid_ocr_engine.{h,cpp}    保持原检测、识别与文字分段算法
  rapid_ocr_plugin.{h,cpp}    保留插件接口、同步互斥与失败恢复
```

### 同等工作量对照

旧版可通过 `MARK_SHOT_PINNED_AUTO_OCR=1` 启动自动识别，因此额外建立两版都做 OCR 的对照。全部采用 Release 应用和 Release 插件；三轮交错启动，每次七秒，稳定值为三秒后样本中位数，再取三轮中位数。图片和模型相同，自动翻译关闭，不连接桌面或网络。

| 完整应用条件 | 内核高水位 | 稳定 RSS | 稳定匿名驻留 | 稳定 PSS |
| --- | ---: | ---: | ---: | ---: |
| 0.1.61，默认不做 OCR | 58.48MiB | 58.48MiB | 15.17MiB | 43.30MiB |
| 0.1.61，开启自动 OCR | 206.45MiB | 91.55MiB | 29.79MiB | 75.97MiB |
| 当前修改前基线，自动 OCR | 206.28MiB | 91.31MiB | 29.50MiB | 75.79MiB |
| 仅分阶段、准入和输入共享 | 176.82MiB | 90.93MiB | 29.04MiB | 75.31MiB |
| 正式局部 C API 实现，自动 OCR | 177.75MiB | 64.61MiB | 17.84MiB | 49.00MiB |

相同 OCR 工作量下，正式实现相较当前基线的稳定 RSS 下降约 **29.2%**，峰值下降约 **13.8%**；相较旧版开启 OCR 也改善。与旧版默认不识别相比，稳定 RSS 仍高约 **6.13MiB（10.5%）**，但不再接近此前约 56% 的额外驻留。推理高水位仍高于不执行 OCR 的窗口，这是新增工作量，不应把两者的峰值差异直接命名为泄漏。

本轮结果：`results/release-capi-summary.json`，探针：`compare_release_capi.py`。此前 `results/cli-capi-summary.json` 使用 Release 应用搭配 Debug 插件，只作为中间诊断，不能充当同构建性能结论。

正式 Release 插件与输入共享版本另做三种图片、各三轮的完整输出对照：18 次调用的对应 token 文字、坐标、置信度全部精确一致。密集文字延迟中位数 656→687ms，大文字 260→282ms，空图 134→134ms；该小样本显示回收运行库会增加约几十毫秒延迟，不能宣传为识别速度优化。数据为 `results/ocr-release-capi-summary.json`，构建参数及产物 SHA-256 为 `results/release-capi-artifacts.json`。

### 插件扫描污染的修复

把运行库放入插件目录后，真实多窗口测试先得到失败：OCR 完成且 `unload()` 返回成功，ONNX 映射仍然存在。根因是默认 `QPluginLoader` 在只读取元数据时已经将 `PreventUnloadHint` 写入同文件共享句柄；普通 `QLibrary` 无法通过后续 `setLoadHints` 消除已有标记。符号链接也会经规范路径合并，不能可靠规避。

注册器现先创建不带路径的加载器、清空默认标记，再关联路径；只有实际带 Qt 插件元数据的候选才在加载实例前添加常驻标记。因此已有 provider 接口和静态字符串寿命不变，同目录非插件运行库则可以按任务释放。

真实回归先失败、修改后通过，日志为 `results/private-runtime-{red,green}.log`。另有无模型 fixture 的八种模式、每种三个独立进程：24 次均符合预期，排除推理模型因素。详细源码证据和边界见 [OCR 运行库寿命](ocr-runtime-lifetime.zh-CN.md)。

### 依赖发布边界

插件不再直接链接 ONNX，原来仅依赖 ELF/PE 导入扫描的打包流程会遗漏它。已调整 Windows 部署、Debian、RPM、Arch 和 AppImage：有原生 OCR 插件时显式携带或声明运行库，Windows 还递归解析其依赖。Debian 从构建用开发包元数据推导 ABI 包名和最低版本，不固定猜测发行版包名。

Windows 脚本回归 18/18、Debian 解析测试 3/3 通过；尚未在 Windows 或 Debian/Fedora 原生环境构建安装包。Arch 在 `package()` 根据实际内容补充最终 `.PKGINFO` 依赖，不把条件生成值伪装成静态 `.SRCINFO` 信息；干净环境缺少 ONNX 开发库时仍沿用已有可选插件策略。AppImage 条件分支和各发行版的完整安装验证仍有环境限制。
